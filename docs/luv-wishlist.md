# luv wishlist

This list collects what Luv in Space builds for itself but would better live in [luv](https://github.com/mbrock/luv), so that other luv programs could share it. Every item is backed by a finding in `docs/luv-capabilities.md` (cited by section or run) at luv revision `6abc9d10ec8991c2cfe92888b84946372d6030b9`. Nothing here changes `../luv`; the workaround lives in this repo until luv offers the item, and then this repo switches over.

## Packaging and tooling

luv's flake and live image are built around luv's own games; a dependent repo copies parts of them.

- `applicationPackage` as a flake output (`lib.applicationPackage { src; system; entry; … }`): today it is a `let` binding inside `outputs`, so this repo copies ~120 lines of recipe into `flake.nix` (Packaging; `decision 1: How the game consumes luv`). Why in luv: every luv game needs the same dumped image, FASL cache, fonts and launcher.
  - Runtime data directories as an argument (e.g. `dataDirectories = [ "assets" ]`), installed and exposed to the image the way `fonts/` is. Today the recipe deletes every top-level entry of its copied tree but `fonts/` after the dump (`../luv/flake.nix:720`) and points the image at the rest through `LUV_PROJECT_ROOT` (Packaging). Why in luv: any game with textures, tables or sounds needs them at run time. Workaround here (built): the copied recipe in `flake.nix` moves `assets/` out of the tree before the delete and installs it to `$out/share/luv-in-space/assets`, the launcher exports `LUV_IN_SPACE_ASSETS`; `assets-root` in `src/assets.lisp` reads it and falls back to the system-relative `assets/` in the dev shell (`docs/architecture.md` "Module layout" → "Assets"; `decision 13: Asset storage and attribution`). Smallest step: keep the listed directories next to `fonts/` and give the image one function returning an installed data directory by name, so the same call works in the dev shell and in the package.
- An output directory for the Objective-C exception bridge (`../luv/objective-c/exception-bridge.lisp` writes `../build/objective-c-exception-bridge-*.dylib` next to luv's sources; Platforms). Why: a dependent repo loads luv from the read-only flake input, so on Darwin the bridge can't be written there. Workaround here: on Darwin `flake.nix` loads luv from a writable copy (package `$out/share/luv`, dev shell `~/.cache/luv-in-space/luv-<rev>`, check `$TMPDIR/luv`); untested without a Mac.
- luv's Lisp sources as a package or `lib` attribute for `CL_SOURCE_REGISTRY` (Packaging). Why: dependents now point at the input's source tree by convention.
- A `checks` helper that renders headless on lavapipe in the Nix sandbox (Screenshots; run 27). Why: any luv program wants a GPU smoke test in `nix flake check`.
- Launchers that replace `LD_LIBRARY_PATH` instead of prepending to it (run 5). Why: a host `LD_LIBRARY_PATH` makes luv's own `nix run` die before its first frame.
- `./sly` with a configurable root and build directory, and `play`/`screenshot`/`stop-playing` through a registered application protocol instead of forms naming Luvcraft, Luft and Luvland (Live image; runs 24, 25). Why: other games could use the live image as is; this repo instead dumps luv's `sly-client` with five functions redefined and keeps an adapted `sly-server.lisp` (`task 26: Live image dev loop for luv-in-space`; run 34). Smallest step: a `sly-client` entry point taking the root and an application's play/stop/capture forms from the environment or a file, and `sly-server.lisp` taking the root and system from the environment.
- `./sly status` or `./sly failures` reporting failed live artifacts (run 21). Why: a broken shader redefinition is silent today; the last good pipeline keeps drawing. Workaround here: `luv-in-space:report-failed-live-artifacts`, called by our `./sly status` (`task 28: Live image: report failed live artifacts`).
- `./sly failures` printing `~%` literally (run 22): a small format bug.
- Test and build targets with an output directory option (Screenshots, tests; runs 11–15). Why: they write into `<checkout>/build/`, so running them against a read-only or shared checkout needs a clone.
- Game outputs in the binary cache for `x86_64-linux` (runs 2–4). Why: `nix run github:mbrock/luv` builds locally despite the cache.

## Rendering

luv's HAL is a good base; these are the pieces every 3D program on it rewrites.

- A camera and projection helper with reversed-Z and an infinite far plane, and the Vulkan clip-y convention inside it (Rendering; runs 29–31; `decision 4: Depth strategy`). Why: each game builds its own clip rows and has to discover the y flip and the depth precision trap.
- Double-precision camera-relative positions: a helper that takes `double-float` world positions and a camera and yields single-float camera-relative ones (Double-precision positions; `decision 5: Precision of positions`). Why: any large world (Luvcraft's frontier included, at scale) meets single-float limits.
- Sphere primitives: UV/icosphere mesh generation and a ray-traced sphere impostor shader function with `:frag-depth` (Spheres and planet surfaces; runs 30, 32). Why: planets, balls and markers are common; the impostor is round at every distance. Workaround here: `src/impostors.lisp` (~170 lines: the block per sphere, the quad or full-screen form, the pipelines) and ~165 lines of shaders in `src/shaders.lisp` (the view ray from `:frag-coord`, the stable near root, the far root, the normal, reversed-Z `:frag-depth`).
- Mip levels on Vulkan textures and their generation (a `generate-mipmaps` on upload, or levels in `write-texture`) (Spheres and planet surfaces; `task 115`). Why: `../luv/hal/vulkan/gpu.lisp` writes mip 0 only, so any minified texture shimmers. Workaround here: `downsample-pixels` in `src/assets.lisp` makes a 1/8 copy on the CPU and the Earth shader mixes the two by footprint with `sample-level` 0.
- Mesh primitives: generators for boxes, tubes, frustums, hemispheres, discs and rectangles with normals and parameters, a transform (origin, basis, scale), and instanced unit primitives with a per-instance transform (Instancing many objects; `task 116`, `task 117`). Why: every program with built objects writes them; luv has no mesh library. Workaround here: `src/meshes.lisp` (~800 lines with the Mule's model, the decal and its draws; ~300 of them the generators and instances) and ~160 lines of ship shaders in `src/shaders.lisp`.
- Line and point rendering: either `:line-list`/`:point-list` topologies in the backends or a screen-space ribbon helper (Orbit lines and markers; run 32). Why: the backends accept only triangle lists and strips.
- Back-face culling as a pipeline option (Other findings; run 30). Why: closed meshes pay overdraw, and debugging depth issues is harder without it.
- Scalar and integer vertex formats (`:float32`, `:uint32`) (Starfield; `task 113`). Why: `:float32x2` to `:float32x4` only, so a per-instance scalar is packed into a vector's spare lane. Workaround here: `src/stars.lisp` packs the magnitude excess into the direction's w.
- More blend modes, at least additive (Rendering). Why: premultiplied alpha with alpha 0 works but is a trick.
- Shader-language operators `atan`/`atan2`, `asin`, `acos`, `tan`, scalar–vector broadcasting for `-`, and `let` at statement level (run 32). Why: spherical coordinates and common maths need polynomial workarounds today.
- Texture loading from image files into a texture (Rendering, image loading; run 32). Why: `sdl3-image` is already loaded; every program writes the same decode, convert and rank-2 array copy. Workaround here: `load-image-pixels` in `src/assets.lisp` (`img-load`, `convert-surface` to ABGR8888, a typed copy by row pitch, both surfaces freed; ~0.14 s for 5400×2700) and `texture-from-pixels` in `src/gpu.lisp`.
- The instanced world-text run (`make-world-text-run`) and HDR/bloom/tone-map passes moved from `luvcraft/core` into a loadable system (HUD and instruments; Sun glare). Why: this repo copies ~400 lines of text code and ~250 of post-processing that only exist inside the block game. Workaround here for the post-processing: `src/post.lisp` (~150 lines: exposure rule, bloom chain, tone-map pass) and its shaders in `src/shaders.lisp` (~90 lines).
- `:load-op :load` for colour attachments in the Vulkan backend, and bind group indices above 0 (Rendering; `task 111: post.lisp: HDR target, bloom, tone map, exposure`). Why: a pass cannot add into an earlier pass's image, so a bloom chain needs extra up levels and every added image a second texture binding. Workaround here: separate up levels in `src/post.lisp`.
- The terminal-wall renderer as a loadable system next to `luv/ghostty` (HUD and instruments). Why: a terminal screen in the world needs ~2,150 lines of Luvcraft code today. Here: no workaround; the terminal screen is cut for that cost (`decision 36: Cockpit instruments: Slug screens, dot-matrix strip, gauges and lamps; Ghostty out`), and a loadable renderer would reopen the question.
- A swapchain generation (or a hook) on the canvas context that changes when luv rebuilds the swapchain (Rendering; `task 142: render.lisp and gpu.lisp: release per-target frame resources and colour views of swapchain textures dropped by a resize`). Why: a `canvas-frame-resource-cache` keyed by swapchain textures keeps the old textures' entries after a resize, and nothing public says they went. Workaround here: `note-swapchain-target` in `src/render.lisp` forgets them when `canvas-extent` changes; a rebuild at the same extent is not seen.
- Vulkan device selection by option (prefer discrete, or by name) (Platforms; runs 7, 8). Why: luv takes the first device, and `VK_DRIVER_FILES` is the only way to choose.

## Input, audio, persistence

Small gaps where luv's SDL3 wrapper stops short.

- Gamepad and joystick events in the canvas protocol (Gamepad and joystick). Why: SDL3 and cl-sdl3 have them; luv initialises video only and drops the events.
- A key-name → layout-character function exported by luv's canvas, e.g. `(canvas-key-name-character canvas :w)` over SDL's `SDL_GetKeyFromScancode` (Windowing and input). Why: a window title or help screen showing keys could show the layout's characters; events carry them, but only once the key is pressed. Workaround here: `window-title` names keys by QWERTY position.
- A small mixer on top of `audio-sink` (several voices, stereo push) (Audio). Why: `audio-sink` takes one mono stream with a pan; every program that plays more than one sound writes a mixer.
- A save-file helper: safe read of one form, atomic write, XDG data path (Save files). Why: Luvcraft's pattern is generic and this repo copies it.
- A fixed-step simulation clock with an accumulator and a step cap (Fixed physics step and time warp). Why: Luvcraft has one inline in its frame function; games need the same thing.
